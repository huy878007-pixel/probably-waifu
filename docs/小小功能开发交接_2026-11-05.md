## 5. VisitorApi 当前草稿契约与待审查点

命名空间 `PortraitRuntime.Unity`，静态类 VisitorApi，Version=1。所有调用在游戏主线程。

| 已写方法 | 当前用途 |
| --- | --- |
| Register(owner,id,Func<object>) | 注册可由原生存档重建的 StoreClient 工厂；不覆盖现有未知 ID |
| Unregister(owner)、内部 Clear | 移除自己工厂及尚未入场的队列实例 |
| Context() | JSON：ready、runId、day、current、preview |
| Enqueue(owner,id,first) | 去重，使用原生 AddNextClient 或 AddClient |
| GetState / SetState | 当前存档 ModData，前缀 `visitor/<owner>/...` |
| Roll(owner,key,percent) | 固定 run/key 的万分位数值；记录原始 roll，避免重复抽取 |
| CountDisplayItem(id) | 只计原生 showcaseElement.childItems 中的物品，不计普通库存 |
| GiveOnce(owner,key,itemId) | 成功放入后才记领取标志；放不下则销毁未放置实例并返回 false |
| CreateCustomer(request JSON) | 生成 DIALOGUE 引导或普通 BUY 客人；后者采用原生上层区顾客预算后乘倍数 |
| SetDialogue(handle,pack,slot,json) | main/accepted/done 三种原生 Dialogue 槽 |
| Say(pack,actor,json) | 空闲时开对话，或接到当前无分支对话末尾，并把原末尾 endAction 移到新末尾 |

QueueWindow 会发 `visitor.queue-window`；节点及选项动作会发 `visitor.action`，内容含 owner（pack id）、actor、node、action。

CreateCustomer request 当前字段：id、guide、name、sprite、faction、owner、tags[]、items[]、budgetMultiplier（限制 1..10）。默认 faction `FACTION_UPPER_LEVEL`，默认原生 sprite `femaleUpper_0`。owner 字段应填真实美化包 Mod ID，注意与 API 的状态命名空间 owner/pack ID 区分。

对话 JSON：

```json
{
  "start": "welcome",
  "nodes": {
    "welcome": {
      "text": "你好，店主！",
      "portrait": "portraits/01-welcome.png",
      "action": "optional-action-token",
      "choices": [{"text":"开始设置","next":"size","action":"optional-choice-token"}]
    },
    "size": {"text":"选择大小。","next":"bye"},
    "bye": {"text":"下次见！","dismiss":true}
  }
}
```

当前接口是草稿，接手必须审查和实测：

- public 接口的 JSON 错误处理还不充分，JObject.Parse/错误节点引用可能抛出；统一可诊断失败，不要崩坏游戏循环。
- Build 未全面验证节点可达性/环路、slot 和 owner 归属；Say 对环路/原生对话中已有 choices 的处理应严格保守。
- Enqueue 判断当前或队列已存在即成功，确认优先入队不会重排、丢失原生剧情人物；测试首次开场与中途重启引导。
- Register 需要测试原生 StoreClientListDict 初始化/读档是否会清空注册；核心重新启用时内容端应重绑。
- CreateCustomer 目前的普通预算模板明确是 StoreClientList.CreateUpperLowerVisitor；对其他阵营不应宣称已泛化。小小恰好为上层区。OverrideBudget 避免重复应用难度加成。
- 礼物库存不足、已有相同物品、重复请求、存档重建要验证；GiveOnce 的成功标志不能在放入失败时提交。必要时补真正的库存事务和可重试领取状态。
- 当前美化包还不消费新增台词事件的 pack/portrait 字段，单靠已写核心代码不会显示小小动作差分。
- 当前 RuntimeApi.Status 尚未公布 VisitorApi 能力，接口文档和 NativeContracts 也未覆盖新 API，应补上。

## 13. 已知重要原生事实与坑

- 当前游戏 Assembly-CSharp.dll SHA256：`e729e715043b51782cb5573d95661653dc2437263c1f789288fd1bec5674ec11`，Build26420766。旧版二进制不一定在机器上，HookContracts 报 available OK 不代表完整跨版本验证。
- 正常对话推进直接调用 DisplayClientText / DisplayerPlayerText / DisplaySecText；DisplayLine 主要供恢复流程。1.6.5 已改为监听三个叶方法，不能回退成只监听 DisplayLine，否则导师差分又会全部不切。
- Restore 会释放并清空 PortraitDisplay 的 renderer 绑定；重新启用美化要通过公开 Sync 重新绑定，同时保留当前剧情差分。
- State/Store/Station 访问用核心 NativeAccess，避免调用会自动创建实例的原生单例 getter。尤其主菜单查询不要构造 PlayerStore。
- 原生橱窗是 EmporiumEntry.Instance.showcaseElement（GameGridInventory），默认7×5；只查它，不凭 sprite 名或是否显示在屏幕上判定摆放。
- 原生 StoreClientList.CreateUpperLowerVisitor 的预算是 RNG(250..300)+day×2，再经过 SetBudget 的难度修正。用 OverrideBudget(已生成值×2) 避免修正重复。
- StoreClient.AddBasicDialog 生成原生 accepted/done 对话；OnDealAccepted 可能把 done 接到 accepted 之后，礼物插入要保留其 endAction。
- 游戏日志可能同时出现其他 Mod 的异常，例如 AutoSortStorage，不能一概归因到本项目；按调用栈和功能证据定位。
